## 1. Назначение и цели

### 1.1 Проблема

При групповых поездках планирование разбросано по мессенджерам, таблицам и заметкам, а расходы считаются вручную. Сложнее всего становится, когда состав группы меняется по ходу маршрута (часть людей едет только в один из городов), платят разные люди и в разных валютах. Существующие сервисы разделения расходов не связаны с маршрутом, а планировщики маршрутов не работают с деньгами.

### 1.2 Цель

Создать веб-приложение, в котором группа совместно ведёт маршрут поездки и её расходы, а система автоматически рассчитывает, кто кому и сколько должен, с учётом участия каждого человека в отдельных частях маршрута.

### 1.3 Задачи

1. Реализовать совместное управление поездкой с ролями и приглашениями.
2. Реализовать маршрут из сегментов, у каждого из которых свой состав участников.
3. Реализовать учёт расходов с несколькими способами деления и корректным округлением.
4. Реализовать расчёт балансов и минимизацию количества переводов между участниками.
5. Обеспечить защиту данных: каждый пользователь видит только свои поездки.
6. Покрыть критичную логику автоматическими тестами и подготовить тестовую документацию.

### 1.4 Целевая аудитория

Группы друзей, семьи, студенческие и туристические группы от 2 до 20 человек, планирующие поездки с несколькими пунктами маршрута.

## 5. Бизнес-правила и алгоритмы

**BR-01. Представление денег.** Все суммы хранятся и обрабатываются как целые числа в минимальных единицах валюты. Использование чисел с плавающей точкой в денежных расчётах запрещено.

**BR-02. Деление поровну.** Сумма A делится на n участников: базовая доля `b = floor(A / n)`, остаток `r = A − b·n`. Первые r участников в детерминированном порядке (по порядку вступления в поездку) получают `b + 1`.
Пример: 1000,00 ₸ = 100 000 тиын на троих → 33 334, 33 333, 33 333.

**BR-03. Деление по долям и процентам.** Доля участника `floor(A · wᵢ / W)`, где wᵢ — вес участника, W — сумма весов. Остаток распределяется по методу наибольших остатков; при равенстве остатков — по порядку вступления.

**BR-04. Инвариант расхода.** Для любого расхода сумма долей строго равна сумме расхода в базовой валюте. Инвариант проверяется на уровне базы данных.

**BR-05. Баланс участника.**
`баланс = оплачено − доли + отправленные переводы − полученные переводы`.
Положительный баланс означает, что участнику должны, отрицательный — что должен он. Сумма балансов всех участников поездки всегда равна нулю.

**BR-06. Упрощение долгов.** Жадный алгоритм: пока есть участники с ненулевым балансом, выбираются участник с наибольшим положительным балансом (кредитор) и с наибольшим отрицательным (должник); формируется перевод от должника к кредитору на сумму `min(|долг|, кредит)`. Результат содержит не более n − 1 переводов. При равных значениях порядок определяется идентификатором участника, чтобы результат был детерминированным.

**BR-07. Конвертация валют.** `сумма_в_базовой = округление(исходная_сумма × курс)` с арифметическим округлением до минимальной единицы базовой валюты. Курс фиксируется в момент создания расхода; последующие изменения курсов не влияют на сохранённые расходы. Доли рассчитываются от суммы в базовой валюте.

**BR-08.** Базовая валюта поездки не может быть изменена после добавления первого расхода.

**BR-09.** Выход или исключение участника возможны только при нулевом балансе.

**BR-10.** Участник со статусом «покинул» не может быть выбран в новых расходах и сегментах, но отображается в существующих.

**BR-11.** Изменение состава участников сегмента не изменяет уже созданные расходы.

**BR-12.** Время элементов маршрута хранится как местное время события без пересчёта часовых поясов (время вылета — по местному времени аэропорта вылета).

**BR-13.** Дата расхода может выходить за даты поездки (например, предоплата брони за месяц до поездки).

## 7. Архитектура и технологии

### 7.1 Схема

```
┌─────────────────────────┐      ┌───────────────────────────────┐
│ Браузер                 │      │ Supabase                      │
│ Next.js (React), PWA    │◄────►│ Auth · Postgres + RLS         │
│ TanStack Query          │      │ RPC-функции · Realtime        │
└───────────┬─────────────┘      │ Storage                       │
            │                    └───────────────────────────────┘
            ▼                                   ▲
┌─────────────────────────┐                     │
│ Vercel                  │─────────────────────┘
│ SSR, route handlers     │────► API курсов валют
└─────────────────────────┘
```

Отдельный бэкенд-сервис не используется. Бизнес-логика разделена на две части:

- чистый TypeScript-модуль денежных расчётов (деление, балансы, упрощение долгов), покрытый unit-тестами;
- Postgres-функции для операций, требующих атомарности и серверной проверки (создание и изменение расхода с долями, вступление по приглашению).

## 10. Тестирование и контроль качества

### 10.1 Уровни тестирования

| Уровень | Инструмент | Объём |
|---|---|---|
| Unit | Vitest | Модуль денежных расчётов: покрытие строк и ветвлений не ниже 90 %. Валидационные схемы |
| Интеграционные (БД) | pgTAP (`supabase test db`) | Политики RLS для каждой таблицы, RPC-функции, ограничения и инварианты |
| E2E | Playwright, Page Object Model | Критические пользовательские сценарии (10.2) |
| Ручное | — | Исследовательское тестирование, кросс-браузерная проверка, мобильные устройства |

### 10.2 Критические сценарии E2E

1. Регистрация → создание поездки → создание приглашения → вступление второго пользователя.
2. Добавление расхода поровну на троих → балансы соответствуют ожидаемым.
3. Деление точными суммами с несходящейся суммой → сохранение заблокировано.
4. Расход в сегменте → по умолчанию выбраны только участники сегмента.
5. Отметка рекомендованного перевода → балансы обнуляются.
6. Наблюдатель не может добавить расход.
7. Пользователь, не состоящий в поездке, не получает её данные по прямой ссылке.
8. Попытка выхода участника с ненулевым балансом → отказ с пояснением.

### 10.3 Процесс

- CI в GitHub Actions на каждый push и pull request: линтер, проверка типов, unit-тесты, тесты БД, E2E.
- Дефекты регистрируются в GitHub Issues с шагами воспроизведения, ожидаемым и фактическим результатом, критичностью.
- Тест-кейсы трассируются на идентификаторы требований данного ТЗ.

## 14. Демонстрационный сценарий

Четверо друзей (Айдос, Дана, Ерлан, Мадина) едут в Турцию на 8 дней, базовая валюта KZT.

- **Сегмент «Стамбул»** (дни 1–4): все четверо. Перелёт Алматы — Стамбул оплачен Айдосом в KZT, отель — Даной в USD.
- **Сегмент «Каппадокия»** (дни 5–8): Айдос, Дана, Ерлан. Воздушный шар оплачен Ерланом в TRY.
- **Сегмент «Анталья»** (дни 5–8): только Мадина, пересекается по датам с Каппадокией.
- Ужин в Стамбуле делится точными суммами, так как один из участников заказал больше.

Сценарий демонстрирует подгруппы, пересекающиеся сегменты, мультивалютность, разные способы деления и итоговые переводы, число которых меньше числа попарных долгов.
