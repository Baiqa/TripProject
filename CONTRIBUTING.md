# CONTRIBUTING

Правила совместной работы над репозиторием TripProject. Обязательны для всех участников команды.

## Задачи и ветки

- Любое изменение связано с ID задачи (`T-ID`) или требования (`AUTH-01`, `TRIP-03`, `MEM-05` и т.п. — см. `docs/tz.md`).
- Основная ветка — `main`. Прямые коммиты и пуши в `main` запрещены; все изменения идут через Pull Request.
- Имя рабочей ветки: `feature/<ID>-<короткое-описание>`, например `feature/MEM-01-invite-link`, `feature/T07-rls-trip-members`. Для исправлений — `fix/<ID>-<описание>`.
- Защита ветки `main` (required PR review, запрет force-push) включается в настройках репозитория ответственным за доступ (см. `docs/team/zadanie-4-competencies.md`, раздел «Репозиторий»).

## Коммиты

- Conventional Commits: `feat(expenses): add exact split (EXP-04)`, `fix(money): ...`, `test(rls): ...`, `chore: ...`.
- Коммит — небольшое завершённое изменение с понятным сообщением и ID задачи/требования в скобках.
- Запрещено коммитить `.env*`, ключи `service_role`, пароли, личные данные пользователей.
- В репозитории хранятся: код, миграции (`supabase/migrations`), тесты (unit, pgTAP, e2e), документация (`docs/`). Сгенерированные файлы (`node_modules`, `.next`, `src/types/database.ts` — только через `npm run db:types`) не редактируются вручную.

## Pull Request / Merge Request

PR содержит:
1. Цель и ID задачи/требования.
2. Краткое описание результата (что реализовано).
3. Способ проверки (какие тесты запущены, что проверить руками).

Проверяющего назначает автор PR при открытии (или по дежурству, см. матрицу функций в задании 4). Согласованный срок ответа на PR — 1 рабочий день с момента назначения.

## Проверка и принятие

- До слияния PR проверяет **другой** участник — не автор.
- Обязательные условия слияния: `npm run typecheck && npm run lint && npm run test` проходят; при изменении схемы БД — `npx supabase db reset && npx supabase test db` тоже проходят; новая таблица содержит RLS-политики и pgTAP-тест (участник видит, посторонний не видит, наблюдатель не пишет).
- Сливает PR автор после одобрения проверяющим (или проверяющий — по договорённости пары на конкретный цикл).

## Конфликты и ошибки

- Спорное изменение автор согласует с затронутым коллегой напрямую, затем повторяет проверку.
- Ошибочное слияние отменяется отдельным коммитом (`revert`), а не перезаписью истории; ответственный за исправление — автор ошибочного PR, если не согласовано иное.

## Изменение договорённостей

- Обновления матрицы компетенций, плана развития и распределения функций (задание 4) проходят ту же проверку, что и код: PR + проверка коллегой.
- Каждое такое изменение фиксируется в журнале (`docs/team/zadanie-4-competencies.md`, раздел «Журнал изменений договорённостей»): дата, что и почему изменено, кем согласовано.

## Практический цикл

Каждый участник обязан пройти минимум один полный цикл: задача → рабочая ветка → содержательный коммит → PR → проверка другим участником → исправления (если есть замечания) → слияние. Каждый участник проверяет минимум один PR коллеги.
